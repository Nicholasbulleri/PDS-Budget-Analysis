Source Priority

Deep analysis of how dim_project resolves attributes from 5 source systems. Verified empirically against live data (4,035 DSSF+Ingenious overlap projects, 2.27M total).

Key finding: field-level COALESCE, not record-level

Different fields in the same row can — and regularly do — come from different source systems. There is no single best_pds_source column in the physical dim_project DDL (it's computed at build time but not persisted). Each field has its own COALESCE chain with a field-specific priority order. A single project row may have its name from DSSF, phase from Ingenious, delivery_model mapped from Clarizen, and market_id from Finance — simultaneously.

How best_pds_source is determined

Extracted from the actual PySpark notebook (dim_project, Command 10). This drives the when(best_pds_source == "X", ...) guards inside each field's COALESCE.

Normal case (Ingenious status is not external-pending):
Ingenious > Clarizen > ProjectApp

When ingenious__status = 'external-pending':
Clarizen > Ingenious > ProjectApp

DSSF and Finance are never part of best_pds_source — they are always consulted via their own explicit positions in each field's COALESCE chain (typically DSSF first or last, Finance always last).

How the when(bps == "X", ...) guard works

The when(best_pds_source == "ingenious", ingenious__field) expression returns NULL when the condition is false. Inside a COALESCE, this means the value is skipped and the next argument is tried. So the pattern COALESCE(bps→clz, bps→ing, dssf) means: if best_pds_source is "clarizen" and Clarizen has a value, use it. If not (either bps isn't "clarizen", or the value is NULL), try Ingenious — but only if bps is "ingenious". Otherwise fall through to DSSF unconditionally.

This means: if a project has best_pds_source = "ingenious" and Ingenious has a NULL city, but Clarizen has "New York" — Clarizen's city is NOT used because the CLZ guard fails (bps ≠ "clarizen"). The field falls through to DSSF. This is a deliberate design choice to avoid mixing PM-system data from a non-preferred source.

Deduplication: multiple IDs from one source

When ID resolution maps multiple source-system projects to the same master_project_id, the system retains all IDs but picks one "best" per source.

How many duplicates?

66 projects have 2+ Ingenious IDs (max 4). 705 projects have 2 Finance IDs. 9 projects have 2 Clarizen IDs. DSSF and ProjectApp are always 1:1.

How is "best" chosen?

For Ingenious (from notebook): non-test first, then status rank: completed(1) > in-progress(2) > scheduled(3) > feasibility(4) > on-hold(5) > external-pending(6) > cancelled(7), then by managed_spend DESC, then created_at DESC.

All IDs preserved

best_*_id picks one ID for field extraction. *_ids arrays store ALL matched IDs. *_count fields track how many. Downstream consumers can access the full set if needed.

Example: PR-034566 (4 Ingenious IDs)

Four Ingenious projects (Emerus Staff Augmentation, OCED - Lynnwood, OCED - Bremerton, OCED - Yakima) all share custom_id = PR-034566. All are in-progress / Construct. The "best" is selected (likely by creation order or internal tiebreak), and its fields flow into dim_project. The other 3 projects' attribute data is effectively discarded at the unified dimension level.

Snapshot Mechanism

How the *_snapshot tables preserve point-in-time history. This is not SCD Type 2 — it's a periodic full-table copy pattern with rolling retention and permanent monthly archives.

Method: Periodic Full-Table Copy

Key distinction. There are no valid_from / valid_to / is_current columns. Each snapshot is a complete copy of the entire base table at a point in time — not an incremental change capture. This is a Periodic Snapshot Fact Table pattern in Kimball terms.

The 3-Step Pipeline Cycle

The Delta table history reveals a consistent, repeating pattern that runs multiple times per day (~every 6 hours).

Step 1 — WRITE (Append full copy)

A full SELECT * of the base table is appended to the snapshot table. Five metadata columns are stamped onto every row: snapshot_date, snapshot_timestamp, pds_gold_snapshot_version, source_table_version, and is_monthly_archive.

Step 2 — DELETE (same-day dedup)

Removes any earlier snapshot from the same calendar day: DELETE WHERE snapshot_date = '<today>' AND pds_gold_snapshot_version < <current>. Only the latest run of each day survives — even though the pipeline fires ~4× daily, one snapshot per day is retained.

Step 3 — DELETE (rolling prune)

Removes old non-archived daily snapshots: DELETE WHERE snapshot_date < '<~30d ago>' AND NOT is_monthly_archive. Daily snapshots are retained for ~30 days, then purged. Monthly archives flagged is_monthly_archive = TRUE are kept permanently.

Periodic — VACUUM

Delta VACUUM runs to reclaim orphaned Parquet files. Default retention of 7 days (604800000 ms) with retentionCheckEnabled = false.

These five columns are appended to every row in gold/core snapshot tables — they do not exist on the base tables.

Retention Policy Summary

Daily Snapshots

Retained for ~30 days. One per day (latest pipeline run wins). Pruned by rolling DELETE when snapshot_date falls outside the window.

Monthly Archives

Flagged is_monthly_archive = TRUE. Permanently retained — excluded from rolling prune. One per month captures the month-end state.

Intra-Day Dedup

Pipeline runs ~4× daily but only the last run wins. Earlier same-day snapshots are DELETEd before the prune step, preventing unbounded growth.

What This Is NOT

Not SCD Type 2

No valid_from / valid_to / is_current columns. No row-level change tracking. You cannot determine which specific rows changed between two snapshots without diffing them.

Not Incremental / CDC

Each snapshot is a full copy of the base table, not just changed rows. Storage is proportional to base_rows × retained_snapshots — e.g. fact_revenue_snapshot holds 2.28 billion rows (103.8M × ~22).

Use case. This strategy is optimized for temporal analysis — "what did the project portfolio look like last month?" or "how did pipeline revenue change week over week?" — rather than granular row-level audit trails. The vw_relevant_revenue_snapshots view makes it easy to compare Current vs Last Month without knowing version numbers.

Concerns & Recommendations

Four critical concerns identified through analysis of the ds_pds_global schema, the dim_project notebook source code, and live catalog data. Each includes evidence, references, and specific remediation steps.

1. Field-Level Source Blending

Problem

A single dim_project row can mix fields from 5 different source systems (DSSF, Ingenious, Clarizen, ProjectApp, Finance) with no provenance columns in the output. Consumers cannot determine which source contributed which value. 68,329 projects have 2+ source systems where blending occurs, and 780 projects have duplicate IDs within a single source requiring deduplication.

Evidence

best_pds_source logic

Notebook Command 10 computes best_pds_source at build time but does not persist it to the physical table. Normal priority: Ingenious > Clarizen > ProjectApp. When Ingenious status is external-pending, Clarizen takes precedence. DSSF and Finance are never part of best_pds_source — they occupy fixed positions in each field's COALESCE chain.

5 COALESCE patterns

Fields follow 5 distinct patterns (A–E): DSSF-first, bps-first, bps-then-DSSF-then-Finance, bps-only, and special/single-source. Each field has its own priority chain — name starts with DSSF, but phase starts with the bps winner. See the Source Priority tab for exact chains.

Notebook author's own To Do

The notebook ends with a candid list of gaps, including: "determine if a project is an actual pds-managed project — we need to be able to SELECT COUNT(*) FROM dim_project WHERE is_jll_pds_managed_project" — this flag does not exist. Also notes currency conversion is not applied to managed_spend.

Unversioned reference tables

8 CSV files (asset_type.csv, delivery_model.csv, fitout_type.csv, industry.csv, project_type.csv, customer_type.csv, service_type.csv, clarizen_markets.csv) are loaded via pd.read_csv() from /Workspace/Shared/PDS/... at runtime. They are not persisted as queryable tables and have no version history.

Recommendations

R1.1 — Add source-tracking columns

For every COALESCE'd field (e.g., name, sector, managed_spend), add a companion {field}_source column. Implementation: duplicate the existing when() chain in Command 11, returning the source name (lit("dssf"), lit("ingenious"), etc.) instead of the value. This makes provenance queryable: SELECT name, name_source FROM dim_project.

R1.2 — Persist reference tables as Delta

Replace the 8 pd.read_csv() calls with versioned Delta tables in the schema (e.g., ref_asset_type, ref_delivery_model). Benefits: auditable change history via Delta time travel, queryable by downstream consumers, and no dependency on workspace filesystem paths. Load once, reference by table name.

R1.3 — Create a field lineage view

Build vw_dim_project_field_lineage that joins dim_project with each source-specific dim via best_*_id columns. For each field, show: unified value, DSSF value, Ingenious value, Clarizen value, and which source won. Enables consumers to validate and debug blended results without writing complex multi-join queries.

R1.4 — Define is_jll_pds_managed_project

Convene a working group to define the business rules for this flag (the notebook author identifies test projects, capital planning, third-party-managed, and no-budget/no-schedule as open questions). Encode rules as a configurable reference table (ref_managed_project_rules) and compute the flag in the notebook. This is the single most impactful improvement for analytics accuracy.

2. Snapshot Methodology Gaps

Problem

The snapshot mechanism uses a periodic full-table copy (not SCD Type 2 or CDC). The retention policy keeps daily snapshots for only ~30 days, then one monthly archive. This means: intra-day changes are lost (last pipeline run wins, ~4 runs/day), and after 30 days, intra-month changes are lost (only month-end snapshot survives). Any analytics requiring "when did this field change?" at finer granularity cannot be supported.

Evidence

3-step pipeline cycle

Delta table history reveals: Step 1 — WRITE (full SELECT * append with 5 metadata columns), Step 2 — DELETE (same-day dedup: earlier same-day snapshots removed), Step 3 — DELETE (rolling prune: non-archived snapshots older than ~30 days removed), followed by periodic VACUUM. See the Snapshots tab for details.

Storage cost

fact_revenue_snapshot holds 2.28 billion rows (103.8M base × ~22 retained snapshots). Each snapshot is a full copy — identical rows are duplicated across snapshots even if they never changed. Total snapshot storage across all 16 gold tables exceeds 2.5 billion rows.

No change detection

There are no valid_from / valid_to / is_current columns. No row-level change tracking. Determining which rows changed between snapshots requires a full-table diff — computationally expensive at 100M+ row scale.

Version tracking

snapshot_version_tracking (28 rows) is the central registry. vw_relevant_revenue_snapshots provides named aliases (Current, Yesterday, Last Week, Last Month) but only 4 are defined — no programmatic way to request "the snapshot from March 15th" without knowing the version number.

Recommendations

R2.1 — Implement CDC for high-value dimensions

For dim_project and dim_opportunity, switch to a CDC-based approach that records only changed rows with valid_from / valid_to timestamps (true SCD Type 2). This captures every change without duplicating unchanged rows. Keep the periodic snapshot for fact_revenue where full-table comparison is the intended use case.

R2.2 — Extend daily retention to 90 days

The current ~30-day rolling window loses intra-month granularity too quickly for quarterly reporting cycles. Extend to 90 days. For dim_project_snapshot (2.27M rows/snapshot), this increases from ~50M to ~200M rows — manageable with Delta Lake compression and Z-ordering on snapshot_date.

R2.3 — Add changed_fields metadata

When writing snapshots, compare each incoming row to the previous snapshot (hash-based or column-by-column) and store a changed_fields array column listing which fields changed. This enables efficient "what changed?" queries without full-row comparison: SELECT * FROM dim_project_snapshot WHERE array_contains(changed_fields, 'managed_spend').

R2.4 — Evaluate Delta Lake Change Data Feed

Databricks natively supports Change Data Feed (CDF) which automatically captures row-level changes (inserts, updates, deletes) with zero additional ETL. Enable with ALTER TABLE SET TBLPROPERTIES (delta.enableChangeDataFeed = true). This is the lowest-effort path to true change tracking on the base tables themselves.

3. Transformation Timing & Performance

Problem

There is no observable scheduling configuration in the repository — no Airflow DAGs, no Databricks Workflow YAML, no cron definitions. The transformation chain (raw → source dims → ID resolution → dim_project → snapshots) has no visible dependency management, parallelism, or performance monitoring. Reference tables are re-read from CSV on every run. All tables are fully rebuilt every cycle (~every 6 hours).

Evidence

No pipeline orchestration

The only scheduling artifact is run_all_refresh.sh — a local bash script that chains Python scripts for dashboard CSV exports. It is not the platform ETL. No Databricks Jobs, Airflow DAGs, or workflow definitions were found in the repository. Pipeline cadence (~6 hours) is inferred from Delta table history, not from any configuration.

No execution telemetry

The notebook calls write_table(final_df, table_name="dim_project") at the end with no timing instrumentation — no start/end timestamps logged, no row count validation, no success/failure alerting. If the pipeline fails silently, there is no mechanism to detect stale data until a consumer notices.

CSV re-reads every run

8 reference tables are loaded via spark.createDataFrame(pd.read_csv("/Workspace/Shared/PDS/.../reference_tables/X.csv")) on every pipeline execution. This introduces latency, bypasses Spark's optimized Delta reader, and has no caching across runs. If a CSV file is accidentally modified or deleted, the entire pipeline fails.

Full-table rebuilds

Every ~6-hour cycle fully rebuilds all source-specific dims, ID resolution tables, and dim_project from scratch. For dim_project_finance (1.77M rows) and dim_project (2.27M rows), this is a significant compute cost when typically only a small fraction of rows have changed upstream.

Recommendations

R3.1 — Implement Databricks Workflows

Define the full pipeline as a Databricks Workflow with explicit task dependencies: source dims (parallelizable) → ID resolution → dim_project → facts → snapshots. This enables correct ordering, automatic retry on failure, email/Slack alerting, and a visual DAG for monitoring. Store the workflow definition as code (YAML or Terraform) in the repository.

R3.2 — Add pipeline_execution_log

Create a pipeline_execution_log Delta table that records: table name, start timestamp, end timestamp, rows read, rows written, duration, and status. Instrument the pds_gold_write.write_table() utility to log automatically. Build a monitoring view or dashboard that alerts when execution time exceeds 2× the rolling average or when data is older than the expected SLA.

R3.3 — Cache reference tables as Delta

Persist the 8 CSV reference tables as Delta tables (overlaps with R1.2). Replace pd.read_csv() calls with spark.read.table("ref_asset_type"). Delta reader is orders of magnitude faster than CSV parsing, and Spark can cache these small tables in memory across notebook cells.

R3.4 — Evaluate incremental MERGE

Instead of full-table rebuilds, use Delta Lake MERGE INTO to process only rows that changed upstream. Requires: (a) reliable updated_at or version column in curated source tables, (b) a watermark tracking the last-processed timestamp. For dim_project_finance, this could reduce the per-cycle processing from 1.77M rows to ~10K changed rows.

R3.5 — Add data freshness monitoring

Create a vw_data_freshness view that compares snapshot_version_tracking.snapshot_timestamp against current_timestamp() for each tracked table. Alert when any table's latest snapshot is older than the expected refresh interval (e.g., 8 hours). Integrate with existing monitoring/alerting infrastructure.

Methodology

How mappings were verified

Rather than relying on column name similarity (which would miss renames like locationname → address), we joined 200–500 matched records through the full resolution chain (curated.project → dim_project_clarizen/ingenious → id_resolution_project → dim_project) and compared actual field values. For each curated field, every dim_project field was scored by the percentage of records where the values matched (exact or substring). A 30%+ match indicates the fields carry the same data. This approach correctly identified non-obvious mappings (e.g., totalapprovedbudgetamount → managed_spend, regionname → market_id) and confirmed false negatives (e.g., stagetext at 0% match with stage because dim only sources stage from DSSF, not Clarizen).
